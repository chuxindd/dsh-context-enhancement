## Q2：N 条 / N tokens 的计算逻辑

### `shadowedItemCount` = `data.shadowedSeqs.length`

**【已证实】** `shadowedSeqs` 是被替换的当前 surface 节点的 seq 数组，顺序为 surface 顺序。计数是**被压缩替换的 surface 项数**，不是对话轮次数。

- 来源：`compaction/summary` 事件的 `data.shadowedSeqs`（`packages/compaction/compaction/src/types.ts:39-40`）
- 提取：`command.ts:115-117` — `data.shadowedSeqs.length`
- 插件侧对应：`src/internal/compaction/region.ts:426` — `selectedNodes.reduce((total, node) => total + node.heuristicTokens, 0)`，`shadowedSeqs` 在 `commitCompactionBody` 写入事件

### `shadowedTokenCount` = 被替换内容的**启发式 token 估算**

**【已证实】** 计算公式：

```ts
// src/internal/compaction/region.ts:426（插件复制品）
// packages/compaction/compaction-basic/src/region.ts:360（DSH 核心）
shadowedTokenCount = selectedNodes.reduce((total, node) => total + node.heuristicTokens, 0)
```

**含义**：
- **不是**输入/输出 token 数；**不是**压缩请求的 provider usage
- **不是**净释放量（需减去 checkpoint 节点的 token 才得到净释放）
- **是**被替换的 surface 节点的**启发式价格之和**（`heuristicTokens` 字段），即这些节点在 token-meter 固定估算器下的估算贡献量
- 与 `shadowedRouteTokenCount`（使用 `node.tokens` 路由价格）区分：前者用于 shadow-price 协议（投影一致性），后者用于 shrink 对比

**参见**：05 文档 Q5 已记录 DSH 轨迹固定文案（"上下文已压缩"等），此文案是 DSH 核心 `ui-chat` 的额外完成状态文案。

## Q3：表示输入、输出或净释放？

**【已证实】既非输入也非输出，也非净释放——是被替换 surface 节点的估算价格和。**

- `compaction/summary` 事件的 `usage` 字段（可选）才携带压缩请求的 provider reported usage（含 input/output），但该字段**不**渲染到 UI
- `shadowedTokenCount` 是纯 surface 价格：等于 `sum(heuristicTokens)`，可理解为"被压缩掉的内容在 surface 上的估算 token 占用"
- **净释放**需要 `shadowedTokenCount - checkpointFramedTokenCount`（summary checkpoint 的 token 估算），但此差值**不**在 UI 中显示

## Q4：是否记录压缩前后 surface？

**【部分已证实】压缩前 surface 通过事件日志可推导，压缩后 surface 隐式为新 checkpoint 节点。**

| 信息 | 记录方式 | 可访问性 |
|------|----------|----------|
| 压缩前被替换节点 | `shadowedSeqs` 数组 + `shadowedRange` 范围 | `compaction/summary` 事件持久化 |
| 压缩后替代节点 | checkpoint `user/message` 事件 | `session.append` 的 `surfaceOp` 写入 |
| 压缩前 surface 总量 | 可通过 `tokenMeter.measure(session)` 在事件前快照获得 | 不持久化在事件中 |
| 压缩后 surface 总量 | 可通过 `tokenMeter.measure(session)` 在事件后快照获得 | 不持久化在事件中 |
| 压缩前后 token 投影 | `contextPressure` 投影维护 `projectedTokens` | 通过 projection 增量更新，不单独记录每次压缩的差值 |

**结论**：事件日志包含足够信息重建压缩前后的 surface 构成（通过 `shadowedSeqs` + event replay），但没有**直接**记录"压缩前 token 总量"和"压缩后 token 总量"的字段。

## Q5：能否区分工具摘要 / 裁剪 / 遗忘 / overflow？

### 插件侧：能区分——通过 `SurfaceSourceKind` 溯源分类

**【已证实】** `src/internal/compaction/source-index.ts:13`：

```ts
type SurfaceSourceKind = 'original' | 'tool-summary' | 'tool-pruned' | 'history-summary' | 'unknown-replacement'
```

| 类型 | 判定逻辑 | 文件行号 |
|------|----------|----------|
| `original` | 不是 `user/message` replacement 或不匹配任何已知来源 | `source-index.ts:100` |
| `history-summary` | `isCompactCheckpointSource(source)` — compaction checkpoint | `source-index.ts:99` |
| `tool-summary` | 审计记录匹配的工具组摘要替换 | `source-index.ts:107` |
| `tool-pruned` | `wasPruned()` — 前一个事件是 `compaction/prune` 且指向同一节点 | `source-index.ts:108` |
| `unknown-replacement` | 第三方替换，来源不明 | `source-index.ts:109` |

### UI 侧：不区分——所有 compaction 显示统一的 "已压缩 N 条" 文案

**【已证实】** `CompactionItem.tsx` 只渲染 `shadowedItemCount` + `shadowedTokenCount`，不区分被压缩内容的来源类型。`shadowedSeqs` 本身不含类型标记。

### 日志侧：可通过事件类型区分

| 事件类型 | 对应能力 | 日志区分 |
|----------|----------|----------|
| `compaction/prune` | 工具结果裁剪（tool-result-pruner） | 独立事件类型，含 `shadowedSeqs` |
| `compaction/summary` | 历史对话摘要（compaction-basic） | 独立事件类型，含 `shadowedSeqs` + `summary` |
| 工具组摘要替换 | 语义工具组摘要 | `tool/result` replacement + 审计记录 |

**结论**：底层事件类型可以区分工具摘要、裁剪、历史遗忘，但 UI 不做此区分。

## Q6：能否凭现有日志重建一次维护决策？

**【已证实】可以——通过 Session 事件日志 + 审计存储可完整重建。**

### 可重建信息

1. **每次压缩决策**：`compaction/start` → `compaction/summary` → `compaction/end` 三事件序列完整记录触发时机、被压缩范围、结果状态
2. **被压缩内容**：`shadowedSeqs` 列出被替换的节点 seq，可通过 `session.eventAt(seq)` 获取原始内容
3. **压缩结果**：`compaction/summary` 的 `summary` 字段包含生成的 checkpoint 文本
4. **shadow 价格**：`shadowedTokenCount` 记录被替换内容的估算价格
5. **工具组摘要审计**：`ToolGroupAuditRecord`（`src/internal/compaction/tool-group-audit.ts:17-33`）记录每次工具组摘要的 requestId、fingerprint、status、replacementSeqs、summary
6. **工具结果裁剪**：`compaction/prune` 事件记录每次裁剪的 `shadowedSeqs` 和 `shadowedTokenCount`

### replay 脚本证明

`scripts/replay-real-session.ts:571-578` 确实从 `CompactionResult` 提取 `shadowedRange`、`shadowedSeqs`、`shadowedTokenCount` 并写入审计报告。

### 限制

- **触发阈值决策过程**不可直接重建：阈值计算（pressure 水位线等）发生在事件前，事件只记录结果
- **batch 选择策略**（哪些 batch 被选中）通过 `compaction/summary` 的 `shadowedRange` 隐式记录，但未显式标注"遗忘区 vs 工具区 vs 最新区"

## 供后续代理直接引用的结论摘要

1. **"已压缩 N 条历史记录（约 N tokens）"文案来自 DSH 核心** `packages/client/ui-chat/src/client/locale.ts:62`，由 `CompactionItem.tsx:41-45` 渲染。插件代码中**不包含此文案**。
2. **N 条 = `shadowedSeqs.length`**：被 compaction 替换的 surface 节点数（`command.ts:115-117`）。
3. **N tokens = `sum(heuristicTokens)`**：被替换节点的启发式 token 估算和，**非**输入/输出/净释放（`region.ts:426`）。
4. **插件能区分压缩类型**：`source-index.ts` 的 `SurfaceSourceKind` 区分 `tool-summary`/`tool-pruned`/`history-summary`/`unknown-replacement`/`original`。但 UI 不做此区分。
5. **压缩前后 surface 可推导**但未直接记录；需通过事件 replay + tokenMeter 重算。
6. **维护决策可重建**：Session 事件日志 + 审计存储提供完整证据链，可重建每次压缩的输入（被压缩内容）和输出（checkpoint 摘要），但触发阈值过程本身不在日志中。
7. **插件状态面板**显示四个能力计数（`effect-projection.ts`）：taskStateBasic（摘要版本数）、taskStatePrompt（请求参与次数）、toolResultPruner（裁剪次数）、compactionBasic（压缩次数）。
