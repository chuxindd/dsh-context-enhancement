## 2. "latest stable" 选择

- 【已证实】**task-state 侧没有"多候选挑最新"这回事**：每个 session 在 `sessions` 表里**只有一条**记录（`table.get(session.id)`），不存在扫描/排序/版本比较：
  - `recordFor(session)`：`table.get(session.id)` → lifecycle 不匹配（`createdAt` 或 `cwd` 不同）则视为**不存在**（`service.ts:455-465`）。
  - 启动播种与运行期播种都走它：`service.ts:187-193`（init 对 `ctx.sessions.list()` + `createdDuringOpen`）、`service.ts:387-397`（`runtimeFor` 内补种）。
- 【已证实】唯一存在"挑最新一条"的地方是 **audit**：
  - `selectRepairRow(rows, committedRevision)`：在**未 finished** 且 `request.revision === committedRevision` 的行里，取 `time` 最大（并列时 requestId 字典序最大）→ 精确选 1 条（`contract/audit.ts:229-254`）。
  - `highestCertifiedRevision(rows)`：取 success/manual/repair 的最高 revision（`audit.ts:218-227`）。
  - 二者都先按 lifecycle 过滤：`rowsForLifecycle` 要求 `session.createdAt` 与 `session.cwd` 全等（`audit.ts:262-269`）。
- 【已证实】**tool-group audit 的"挑最新"是隐式的**：`successfulAuditFor` / `recoverableOpenAuditFor` 用 `Array.find` 取**第一个**匹配项（`tool-group-audit.ts:95-107`），顺序 = `table.entries()` = Map 插入序 = JSON 文档键序（`storage-domain/src/domain.ts:292-295`；`storage-json/src/format.ts:76-86` 按 `Object.entries` 装载）。
- 【待深挖】tool-group audit 记录**根本没有时间戳字段**（`tool-group-audit.ts:17-33` 无 `time`），因此"第一个 open 记录"与"最新的 open 记录"是否总相等，取决于插入序在整文件重写后是否严格保持。同一 fingerprint 理论上可并发产生多条 open（每次 `tg-${randomUUID()}`，仅当 `priorOpen` 命中才复用 id，`compaction-basic.ts:1117-1128`）；本条未做磁盘/并发验证。

## 4. session replay 是否重复更新或注入

- 【已证实】**回放不会触发任何更新**：DSH 构造器种子事件从不重新发布 `session/event`（`03-Session持久化与回放.md` Q8；`packages/core/session/src/index.ts:454-475` 源码注释）。插件唯一的推进监听是 `session/event`（`service.ts:409-425`），因此重放历史既不会开启 batch，也不会重复提交。
- 【已证实】**重启恢复不调用模型、不重新 fold、不重放未完成更新**：模块头明确"no model call, no history fold, no unfinished-update replay"，只把 lifecycle 匹配的存储记录直接播种为指针（`service.ts:11-20`）；README 同义表述（`README.md:77`）。
- 【已证实】**cursor 续接而非重折**：播种指针的 `sourceCursor` 就是 `committedCursor`（`service.ts:353` 注入 `committedCursor: id => this.publishedStable(...)?.sourceCursor ?? -1`），fold 只取 `event.seq > cursor`（`batch.ts:97-99`）。⇒ 已折叠事件不会二次进入摘要输入。
- 【已证实】**重复注入防护**：播种用 `runtime.stable === undefined` 守卫，同一 runtime 只播种/通知一次（`service.ts:387-397`）；重启后是全新 runtime，故恰好通知一次。
- 【已证实】**插件不往 Session log 写 task-state**：全仓 `session.append` 命中只在 compaction 侧（`tool-result-pruner.ts:350,355`、`internal/compaction/region.ts:259,285,293,523,538`、`internal/compaction/tool-group-replacement.ts:120,125`）；task-state 模块声明**零** `SessionEventMap` 成员（`task-state-basic.ts:11-13`、`task-state.ts:9-12`、`contract/audit.ts:22-25`）。
- 【已证实】**控制流不再发 baseline 陈旧帧**：baseline 由"当前 live 会话 + 内存指针"构造（`internal/task-state/control/service.ts:108-118`）；若 baseline 早于播种（重启竞态），播种通过 `notifyCommitted` 补发 `update` 帧（`service.ts:554-567, 387-397`）。测试证据：`tests/task-state-restart-recovery.spec.ts:215-268`（重启后 baseline 精确映射到各自 stable）、`:270-314`（baseline 为 null 后被 update 水合）。
- 【待深挖】**重启后积压尾部不会自行推进**：worker 构造只计算 `pendingEligible`（`worker.ts:103-108`），`maybeSchedule` 的唯一调用点是 `session/event` 观察者（`service.ts:422-424`）。⇒ 重启后若 cursor 之上已有 ≥ `minEvents` 的 eligible 事件，也要等**下一个** eligible 事件到来才会 fold。模块注释承认该设计（`service.ts:18-20`），但没有测试覆盖"重启后积压自动成批"。
- 【已证实】compaction 侧重启重复防护：`shouldAttemptToolGroupSummary` 对同 fingerprint 的 success 不再尝试、open 且已落 replacement 视为 served、fallback 永久放弃、failure 最多重试 2 次（`tool-group-audit.ts:109-144`）；`isServedAudit` 在 `commitToolGroupSuccess` 失败后仍以 open+replacementSeqs 证明"已落地"（`tool-group-audit.ts:118-124`；`compaction-basic.ts:1208-1237`）。

## 5. 两个 DSH 是否共享

- 【已证实】**共享，条件只是同一个 `$DSH_HOME`**：storages 根不按 profile / workspace / session 分片（`packages/bundle/base/cordis.patch.yml:151`；`home-paths/src/index.ts:79-98`），domain 名是常量，`sessions` 表键是裸 SessionId（`domain.ts:42`）。⇒ 桌面端 + 终端 `dsh`、web 服务 + headless 同 `$DSH_HOME` 时**写同一个文件、同一批记录键**。
- 【已证实】**互斥只存在于进程内**：
  - `DomainFacility.reserved` / `domains` 是进程内 Map，并发 `open` 同名 domain 报 `already-open`（`storage-domain/src/index.ts:70-72, 104-107, 156-160`）。
  - `JsonStorageBackend.open` / `opening` 也是进程内 Map，重复 open 同一 unit 报错（`storage-json/src/index.ts:40-62`）。
  - 【未找到】任何跨进程锁/注册表（`flock`、lockfile、PID 文件、实例 id、文件身份校验）——插件全仓 grep `flock|lockfile|fs.watch|watchFile|mtime|rename` **零命中**（除 domain 相关 `revision !==` 判断）。
- 【已证实】**共享的后果是"整文档后写覆盖"而非"行交错"**：
  - 每次 put 都把**整个 state**（该 domain 全部表全部记录）序列化后原子替换文件：`serialize(descriptor.name, this.state)` → `writeAtomic`（`single-unit.ts:140-147`；`atomic.ts:24-40`）。
  - `atomic.ts:7-10` 的注释直接写明该协议的前提假设："a unit file has exactly one writer per process and last-write-wins is correct"。插件的部署形态（两个 DSH 同 `$DSH_HOME`）**违反**这条假设。
  - 数据丢失机制：进程 B 在 open 时装载快照，A 之后写入的记录不在 B 的内存里；B 的**任何**写入（哪怕是为别的 session）都会整文件重写并**静默抹掉 A 的记录**（`domain.ts:307-313` + `single-unit.ts:141`）。实测该文件承载 **180 个互不相关 session** 的记录，故一次覆盖可牵连上百会话。
- 【已证实】Session log 与 storage 文件**同时**被两个实例共享（都在 `$DSH_HOME` 下），两种失败模式会叠加（见第 8 节）。
- 【未找到】任何针对多实例的测试或文档：`tests/` 中 `two processes|second process|concurrent instance|multi-instance|cross-process` 零命中；插件 `*.md` 中 `multi-instance|same DSH_HOME|last-write-wins|no file lock` 零命中。重启测试用的是"同一 root 下 dispose 再 mount 新 Context"（`tests/task-state-restart-recovery.spec.ts:132-171, 215-268`），**不是两个并发进程**。

## 6. 锁、revision/CAS、原子提交

- 【已证实】**进程内锁（三层，均不跨进程）**：
  1. domain 级单写链：`private chain: Promise<void>`，所有 put/delete/update/setGlobal 排队（`storage-domain/src/domain.ts:148-151, 263-270`），且**先落盘后改内存再发事件**（`:307-313, 332-346`）。
  2. 会话级单飞 + 串行链：`TaskStateWorker` 的 `active` 单飞守卫、`chain` 串行、`enqueueMutation` 让 manual edit 排队在同一链上（`worker.ts:68-75, 122-130, 171-172, 204-226`）。
  3. compaction 侧的持久化 bracket 锁复用 Session log 的 `compaction/start|end`（`internal/compaction/region.ts:259-303`；`02-Compaction与Replacement.md` Q5）——DSH 层面就无跨进程语义（`03` Q6）。
- 【已证实】**revision 是推导值，不是 CAS**：`targetRevision = (attempt.base?.revision ?? 0) + 1`（`update.ts:152`），base 来自内存指针（`worker.ts:267` 在 cycle 开始时 `readBase`；launch 时只用于 fold 的 `cursor`/`base` 快照，`worker.ts:174-182`）。
- 【已证实】**权威写没有版本比较**：`putStable` 做 `table.get` → 仅校验 lifecycle → `table.put`（`service.ts:519-541`），**不比较** `existing.stable.revision` / `sourceCursor`，也不用 `table.update` 做 CAS；`publishCommitted` 无条件把收到的 stable 设为指针（`service.ts:544-552`）。
- 【已证实】**存在 CAS 形状的只有 audit 行**：`finishOpenAudit` 在 `audit.update(key, current => rejected ? current : finishAuditRow(...))` 的回调里逐字段拒绝（requestId、lifecycle、target revision、finished 是否已存在）（`service.ts:287-308`），拒绝即原值返回 = 进程内原子的 compare-and-set（依赖 `domain.ts:332-346` 的链上 RMW）。manual edit 的乐观并发是 `current.revision !== request.expectedRevision`（`service.ts:629-631`），比的是**内存指针**而非介质。
- 【已证实】**一次提交不是单一原子事务**：`sessions` 行 put 与 `audit` 行 finished put 是两次独立 put，源码显式声明"表间无原子性假设"（`contract/audit.ts:12-15`；`domain.ts:13-15`）。崩溃/失败落在两次 put 之间的语义：stable 已提交、audit 仍是 open ⇒ 启动期或实时"补证"（`service.ts:232-258` 启动、`265-284` 实时、`update.ts:461-489` 记 `auditGap`），**永不回滚已提交 stable**。
- 【已证实】**单次 put 的物理原子性有保证**：临时文件（`wx`）→ `handle.sync()` → `rename` 覆盖 → POSIX 再 fsync 父目录；失败清理 temp（`atomic.ts:24-52`）。`close()` 前 drain 在飞的 publish（`single-unit.ts:115-123`）。
- 【已证实】**"先审计后调用模型"的顺序保证**：open 审计行必须 await 成功才允许 dispatch（`update.ts:154-180`），失败即 `stage:'request', code:'AUDIT'` 中止，模型不会被调用。⇒ 已提交的 stable 必有 open 行（`contract/audit.ts:16-22`），repair 无需凭空造凭证。
- 【待深挖】上述"进程内 revision 单调"是**链式串行化的涌现属性，不是被断言的 invariant**：`putStable`/`publishCommitted` 都不拒绝更低 revision 的写入。任何新增调用方（或跨进程写者）都能写回旧版并被直接发布。

## 7. 缓存失效与外部写入可见性

- 【已证实】**domain 层没有任何新鲜度检查**：记录只在 `open()` 时 `loadAll()` 读一次（`storage-domain/src/index.ts:117-143`），此后不重读、不比对 revision/mtime/ino，也**没有** `fs.watch`/`watchFile`/inotify 的替代路径（`storage-domain/src/**`、`storage-json/src/**` 全无监听；插件 `src/**` 同样为零）。
  - 对比：DSH Session log 侧至少还有 `readStableFile` 的读前后 stat 重试（`03` Q6；`session-persistence-jsonl/src/index.ts:310-322`），**storage-domain 连这个都没有**。
- 【已证实】⇒ 外部进程写入**在本进程重启/重新 mount 之前完全不可见**；而本进程的下一次写入会把外部写入**整文件覆盖**（第 5 节）。既没有失效通知，也没有"介质已变更"检测。
- 【已证实】插件在此之上再加一层进程内缓存：指针 `runtime.stable` 与 `recordFor`/`rowsForLifecycle` 都读 domain 内存镜像（`service.ts:387-397, 238`）⇒ 长命进程对外部变更的可见性最多等于 domain 的可见性（即：零）。
- 【已证实】恢复手段只有一次重新 open：进程重启、provider 卸载重挂（dispose 链 `service.ts:167-179` + `domain.close()`）都会重新 `loadAll()`；失败后不会自动重开（`service.ts:150-165`）。

## 8. cursor 倒退 / 旧版覆盖 / 分叉防护

- 【已证实】**真正实现的强防护是生命周期围栏（不是版本围栏）**：
  - 读：lifecycle 不匹配的记录读作不存在（`service.ts:461-463`）。
  - 写：拒绝用本 lifecycle 的 stable 覆盖同 id 的**另一个 lifecycle** 记录（`service.ts:526-533`）。
  - audit：repair 只在 lifecycle + target revision 全等时才写（`service.ts:296-307`；`audit.ts:241-254`）。
  - 测试：`tests/task-state-restart-recovery.spec.ts:316-357`（不同 createdAt 不串台）、`:472-536`（同 id 替换期间新旧 runtime 不互相污染）。
- 【已证实】**没有 revision/cursor 倒退防护**：`putStable`、`publishCommitted` 均无单调性断言（第 6 节）⇒ 旧版覆盖在服务端不被拒绝；唯一的旧版覆盖防护在**客户端镜像**（`client/task-state-control.ts:141-149`，`revision <= current` 直接丢弃）。
- 【已证实】由此产生的分歧场景（多实例覆盖后重启）：磁盘 revision 倒退 → 服务端指针与 prompt 快照按磁盘（旧），而 UI 镜像保留更高 revision（新）⇒ **页面内容与模型可见摘要短暂不一致**，且客户端不会因收到低 revision 回退。此推理由两处已证实事实组合得出，未见测试覆盖。【待深挖】
- 【已证实】**分叉/重复防护在 compaction 路径上更强**：落 replacement 前必须通过 `assertToolGroupCommitStable`——校验 `sessionId` + `surface.replaceGeneration` + `sourceSeqs` 全等（`tool-group-audit.ts:146-158`，调用点 `compaction-basic.ts:1130`）；配 `shouldAttemptToolGroupSummary`/`isServedAudit` 去重（第 4 节）⇒ 重启或并发下同一组不会被重复归纳。
- 【已证实】**无界增长（观测）**：插件全仓**没有**任何 `table.delete(...)`（grep 零命中）⇒ `sessions` 与 `audit` 记录只增不减；实测 180 + 5335 条。其中 **206 条 audit 行永久停留在 open**（无 finished）；启动 repair 每个 live 会话最多补 1 条（`selectRepairRow` 只认与已提交 revision 相符的那条，`service.ts:239-250`），其余 open 行永不收尾。68.2 MB 文件 ≥ 每次 put 的重写量。
- 【待深挖】跨进程 + 两介质的两阶段提交无共同事务边界：本进程已在 log 落了 replacement，另一进程却把含该 replacement `replacementSeqs` 的 audit 行覆盖掉 ⇒ 该 reduction 变为"未被证明"（`isServedAudit` 假），理论上可被再次归纳（`tool-group-audit.ts:118-144`）。未构造实验，属推理。

## 9. 与 DSH 原生"无跨进程锁"事实的叠加

- 前提事实（`03-Session持久化与回放.md` Q6）：DSH Session log **无 flock / 无 fs.watch / 无跨进程 CAS / 无变更通知**；两进程同写会重复 seq、交错行、且 `rollbackAppend` 截断可能抹掉对方的有效数据。
- 【已证实】插件不改变这一事实，也不弥补它：插件没有引入任何跨进程原语（第 5 节），只是把它复用到了**第二个共享产物**上。
- 【已证实】两者失败几何**不同**：
  - Session log：追加式 → 症状是尾部损坏、seq 重复/断号、被对方 rollback 截断（后缀级）。
  - 插件 domain：整文档覆盖 → 症状是**静默丢记录**（可为无关 session、无关 workspace 的记录），且不带任何错误、日志或序号证据。
- 【已证实】触发条件一次命中两者：同一 `$DSH_HOME`（storages 不分 profile）同时共享 `sessions/**` 与 `storages/*.json`。第二个实例只要**打开同一个 session**，就会一边往 `session.jsonl` 追加、一边整文件重写 domain。
- 【已证实】插件自身**不检测、不报告**多实例：无锁获取尝试、无实例 id、无文件身份比对；冲突只能间接体现在"记录消失/被旧版覆盖"上。
- 【待深挖】叠加后的可观测性：DSH 侧有 `readStoredRevision`/`readStableFile` 之类的比对点，插件侧没有对应点，故多实例问题在插件里没有任何自动告警（只有 domain 打开失败的 loud failure，`service.ts:150-165` 与 `domain.ts:1-5` 的"整文件损坏则大声失败"）。

## 供后续代理直接引用的结论摘要

1. **命名空间与路径**：`context_enhancement_task_state`（`sessions`+`audit`）与 `context_enhancement_tool_group_summary`（`audit`），均 `version:1`、`layout:'single'`（`basic/domain.ts:37-45`；`compaction/tool-group-domain.ts:27-34`）；单位级单文档 `$DSH_HOME/storages/<domain 名>.json`（`storage-json/src/single-unit.ts:33`；`bundle/base/cordis.patch.yml:148-156`）。实测文件 68.2 MB、180 条 session 记录、5335 条 audit 记录、206 条永不收尾的 open 行。
2. **latest stable 选择**：task-state 每个 session 只有一条记录，没有"挑最新"逻辑，只有 lifecycle 围栏（`service.ts:455-465, 526-533`）；"挑最新一条"只出现在 audit repair（`audit.ts:229-254`）与客户端镜像（`client/task-state-control.ts:141-149`）。tool-group 选择用 `Array.find` 取第一条（`tool-group-audit.ts:95-107`），记录无时间戳，最新性依赖插入序。
3. **内存依赖**：只有 JSON 文档跨重启；指针、runtime、水位、单飞链、overflow/pressure memo 全在内存（`service.ts:75-83, 119`；`worker.ts:63-79`；`compaction-basic.ts:235-238`）；读路径同步读内存、永不碰盘（`domain.ts:287-300`；`contract/index.ts:64-70`）；domain 打开失败 ⇒ 永久禁用、不提供 stable（`service.ts:150-165`）。
4. **回放不重复更新/注入**：重放种子不发 `session/event`（DSH 已落库事实）⇒ 观察者不触发；重启恢复直接播种指针、不调模型、不重折、cursor 从 `sourceCursor` 续接（`service.ts:11-20, 353, 387-397`；`batch.ts:97-99`）；task-state 路径零 `session.append`；播种补发 `update` 帧水合重启竞态的 baseline（`service.ts:554-567`；测试 `task-state-restart-recovery.spec.ts:215-268, 270-314`）。**注意**：重启后积压不自行成批，要等下一个 eligible 事件（`worker.ts:103-108`；`service.ts:409-425`）。
5. **两个 DSH 共享**：同 `$DSH_HOME` 即共享同一文件、同一批键（storages 不分 profile，键是裸 SessionId）。互斥只有进程内 `reserved`/`opening`（`storage-domain/src/index.ts:70-72`；`storage-json/src/index.ts:40-62`）。写是**整文档 last-write-wins**（`single-unit.ts:140-147`；`atomic.ts:7-10` 自述假设"exactly one writer per process"）⇒ 后写者静默抹掉对方记录，可牵连上百无关 session。
6. **锁 / CAS / 原子提交**：进程内三层锁（domain 写链 `domain.ts:263-270`、per-session worker 链 `worker.ts:122-130, 204-226`、log 级 compaction bracket）；revision 是 `base.revision+1` 推导（`update.ts:152`），权威 put 无版本比较（`service.ts:519-541, 544-552`）；唯一 CAS 形状是 audit 行的 `update` 回调拒绝（`service.ts:287-308`）+ manual edit 的 `expectedRevision`（`:629-631`）。提交是**两次非原子 put**（`sessions` 与 `audit`，`contract/audit.ts:12-15`），崩溃落在中间由 repair 补证、绝不回滚（`service.ts:232-284`；`update.ts:461-489`）；单次 put 物理原子（temp+fsync+rename，`atomic.ts:24-52`），但每次重写整个 68 MB 文档。
7. **缓存失效/外部可见性**：domain 只在 `open()` 读一次，之后无重读、无 stat 比对、无 watcher（`storage-domain/src/index.ts:117-143`）⇒ 外部写入在重启前不可见，且会被下一次本地写入整文件覆盖；无任何失效或"介质已变更"信号。
8. **倒退/覆盖/分叉防护**：强防护是 lifecycle 围栏 + audit revision 匹配（`service.ts:296-307, 461-463, 526-533`；`audit.ts:262-269`），**没有**服务端 revision/cursor 单调断言（客户端才单调，`client/task-state-control.ts:141-149`）；compaction 侧有 `assertToolGroupCommitStable`（generation+sourceSeqs）与 fingerprint 去重（`tool-group-audit.ts:109-158`）。记录只增不减（全仓无 `table.delete`）。
9. **与 DSH 原生缺口的叠加**：插件不新增也不弥补跨进程原语；同一 `$DSH_HOME` 下一次触发同时命中"log 追加冲突"与"domain 整文件覆盖"两种不同失败模式（后缀损坏 vs 静默丢记录），且插件侧无任何检测/告警点。

## 交给其他任务的问题

1. **多实例写入后果的实测**：需要一次受控实验（两个进程同 `$DSH_HOME`，各持一个会话交替提交），量化"整文件覆盖"实际丢失多少 session/audit 记录，并区分"覆盖丢失"与"双方 revision 都停在 N+1"的表现。属破坏性实验，本轮范围禁止执行。
2. **68 MB 单文档的可伸缩性与写入代价**：每次 put 全量 serialize + fsync 替换；需要测量 P95 写延迟、内存占用（180 + 5335 条记录全驻内存）与崩溃窗口，并评估是否应改 `per-record` 布局或加 audit 的裁剪/归档（当前零 `delete`）。
3. **206 条永久 open 的 audit 行是否应清理**：启动 repair 只处理与已提交 revision 相符的那一条（`service.ts:239-250`）；剩余 open 行既不清也不报警。需要判定它们是崩溃残留还是合法在飞，并决定回收策略。
4. **重启后积压不自动成批是否会漏摘要**：`minEvents` 默认 20，重启后若不再有 eligible 事件，cursor 之上的尾部将长期不折叠（`worker.ts:103-108`）。需要确认这是有意行为还是缺口，并给出"启动后按积压触发一次 wave"的取舍。
5. **tool-group audit 的"第一条即最新"假设**：记录无时间戳、`Array.find` 依赖插入序（`tool-group-audit.ts:95-107`）；需要一个同 fingerprint 多条 open 的场景测试来证明或推翻该假设。
6. **跨进程覆盖与压缩 provenance 的相互作用**：若 audit 行被对方覆盖而 replacement 已在 log 落地，组是否会被二次归纳（第 8 节推理）？需要构造或静态证明 `isServedAudit` 的兜底是否足够。
7. **`putStable`/`publishCommitted` 是否应加单调性断言**：当前进程内单调只是链式串行化的涌现属性，没有 invariant；是否值得在权威写处加 `revision/sourceCursor` 单调校验（并定义其与 lifecycle 围栏的优先级）。
