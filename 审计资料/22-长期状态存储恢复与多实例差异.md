## 1. 逐条差异矩阵

### A. 存储后端与记录键

**A1 · JSON `single` 整文档 LWW（违反 §3.11 第 1、2、3 条）—【确认差异】**
`T basic/domain.ts:40` 与 `C tool-group-domain.ts:30` 都把 `layout: 'single'` 写死；装配层只挂 `storage-json` 且 `backend: json` 无 `routes`（`07-DSH存储域生命周期与并发.md:128-133`、`:183`）。理想方案 §3.11 要求：单实例模式**必须声明 `singleWriterOnly`**，多实例**必须**用记录级后端（优先 SQLite）+ revision CAS + busy retry + 重新读取，否则**必须 fail closed**。
现状：无声明、无租约、无 fail-closed；共享同一 `$DSH_HOME` 的两个进程会各自缓存整份文档并以**整文档后写覆盖**（`07:106`、`:167`；`16-插件摘要持久化与多实例回放.md:89-93`）。实测该文件承载 180 个无关 session 的记录（`16:34`、`:92`），一次覆盖可牵连上百会话。
当前设计事实：这是本主题唯一的**结构性**差异，其余各条多数是它的派生。

**A2 · 记录键 = 裸 `SessionId`，生命周期身份只作值内围栏（违反 §3.11 第 4 条）—【确认差异】**
`sessions` 表键就是 `SessionId`（`T basic/domain.ts:42`、`T basic/service.ts:458`）。理想 §3.11 要求 key 至少包含 `sessionId + lifecycleIdentity(createdAt, cwd, isSeeded, inheritedEventCount)`。
现状把身份放在**值**里（`T contract/types.ts:180-185`）并在读写两侧过滤（读：`:455-465`；写：`:526-533`），因此第二实例写同 id 时两侧**都是合法写**、LWW 生效；身份没有进入键，无法在同一 medium 上并存两个生命周期。同一判定适用于 tool audit：键是 `requestId`，身份在值里（`C tool-group-domain.ts:13`、`:36-44`）。

**A3 · 生命周期身份缺 `isSeeded` / `inheritedEventCount`（§3.11 第 4 条）—【确认差异】（与 A2 同因，单列以便实现对齐）**
`T contract/types.ts:31-36` 只有 `createdAt` + `cwd`。DSH 侧同一概念的身份是四项 `(createdAt, cwd, isSeeded, inheritedEventCount)`（`08-DSH投影缓存恢复与一致性.md:111`；`09-DSH会话ForkResume与血缘.md:171`）。
后果与 DSH 自身的 fence 语义不一致：DSH 把"未播种"与"已播种"视为不同身份，插件视为相同。Fork 子身份天然不同（子是新 id），所以**当前不产生串味**，但该键无法表达 §5.5 的 `inheritedEventCount` 边界，也无法识别"resume 后 fork 前缀被重新播种"的差异。

### B. revision CAS 与提交协议

**B4 · 权威写 `putStable` 不做 CAS（违反 §3.12 第 3 条）—【确认差异】**
`T basic/service.ts:518-541` 的写路径是 `table.get` → 仅校验 lifecycle → `table.put`；目标版本是推导值 `(base.revision ?? 0) + 1`（`T basic/update.ts:152`），base 来自**内存指针**（`T basic/update.ts:68`、`T basic/worker.ts:174-182`、`T basic/service.ts:353-354`）。
理想 §3.12 要求 `WHERE revision = expectedRevision` 的 CAS，并要求"不同进程不能同时从同一 baseRevision 提交两个 `N+1`"。现状既没有介质级比较，也没有单调性断言：任何写者都能写回更低版本并被 `publishCommitted` **无条件发布**（`T basic/service.ts:544-552`）。
派生结论：进程内单调只是"单 worker 串行链"的涌现属性（`T basic/worker.ts:71-75`、`:204-226`），不是被断言的 invariant；服务端对"旧版覆盖"零防护，唯一防护在浏览器镜像（`S client/task-state-control.ts:141-149`）。

**B5 · audit 行确有 CAS 形状，但比较的是进程内内存镜像（§3.12 第 4、5 条）—【等价实现】**
`finishOpenAudit` 在 `audit.update(key, cb)` 回调里逐字段拒绝（requestId 双向、lifecycle、target revision、`finished` 已存在）（`T basic/service.ts:296-307`），拒绝即原值返回。这是 DSH `update` 在写链上的读改写（`07:65`），**进程内**原子且幂等；配合 `finishAuditRow` 的"已结算行不可被 repair 覆盖、repair 可被真实 success 升级"（`T contract/audit.ts:155-166`），满足 §3.12 第 5 条"完成 audit 失败只需 repair"。
但它不跨进程（`07:169`），因此**不能**替代 A1/B4。

### C. stable/audit 原子性与 repair

**C6 · 两次非原子 put + 永不回滚 + 只补证的 repair（§3.12 第 5、6 条）—【等价实现】**
提交序列是：`putOpenAudit`（await 成功才允许 dispatch，失败 → `stage:'request', code:'AUDIT'`，模型不被调用，`T basic/update.ts:156-180`）→ 模型 → `putStable` → `onCommitted` 发布 → `putFinishedAudit`；finished 失败返回 `auditGap: true` 且**禁止回滚**（`T basic/update.ts:450-489`）。
崩溃落在两次 put 之间时：启动 repair 用 `highestCertifiedRevision` + `selectRepairRow` 精确补证"已提交 revision 对应的那条 open 行"，找不到只告警不造凭证（`T basic/service.ts:232-258`、`T contract/audit.ts:218-254`）；实时路径同理（`T basic/service.ts:265-284`、`:295-308`）。这与 §3.12 第 5、6 条**逐字一致**，且 §5.4 明确允许"基础设施不提供跨表事务时仍按 stable 权威 + audit repair"。
与理想方案唯一的结构差是"尽量单事务"：DSH `DomainSpec` 无 `transact`（`07:67`、`:170`），属基础设施缺口而非插件选择。

**C7 · audit 永远不会覆盖或回滚 stable（§3.12 末句）—【等价实现】**
audit 表只在 open/finish/repair 路径被写（`T basic/service.ts:484-516`、`:218-284`），没有任何路径从 audit 反写 `sessions`；`recordFor` 只读 `sessions`（`:455-465`）。audit 行 schema 甚至刻意宽松（`T contract/audit.ts:51-57`），声明自己是 diagnostic-only。附加性质：open 行先于 dispatch 落盘 ⇒ **已提交 stable 必有 open 行**（`T contract/audit.ts:16-22`），repair 无需凭空造凭证。

**C8 · 表间无原子性假设，DSH 侧无共享事务边界（§5.4 "尽量单事务"）—【等价实现】**
domain 头注释显式声明无跨表原子性（`T basic/domain.ts:13-15`）。理想 §5.4 的"尽量"允许退化路径，已由 C6 覆盖；此项只是把"退化的理由"归因到基础设施能力缺失（`07:170`）。

### D. 外部刷新与新鲜度

**D9 · 零新鲜度机制：无 stat 比对、无 watcher、无 refresh（违规 §5.4 "冲突后重新读取"、§9 多实例验收）—【确认差异】**
domain 只在 `open()` 时 `loadAll()` 一次（`T basic/service.ts:149`；DSH 事实 `07:104`、`:121`），此后读全走内存镜像（`T basic/service.ts:455-465`、`T contract/audit.ts:238`）。插件自身也没有任何 `fs.watch`/`mtime` 路径（`16:88`、`:116-120`）。
⇒ 外部写入在**进程重启/重挂之前完全不可见**，而本进程下一次任何写入会把外部写入整文档覆盖。理想 §5.4 的"冲突后重新读 stable、重新折叠未处理窗口"在当前设计里**没有对应实现点**。

**D10 · 指针的内存优先：`readBase` 只读 published 指针（§5.4 CAS 语义）—【需实验确认】**
`readBase` 返回 `this.publishedStable(...) ?? null`（`T basic/service.ts:353-354`），即 **base 来自内存指针，不来自介质**。单进程内"指针 = 最近成功提交"与介质一致（写先落盘再发布，`07:63`、`T basic/service.ts:543-552`）；但若介质被外部替换为更高 revision，下一次 fold 仍从内存旧 base 派生 `revision+1`，可能与介质既有 version 冲突。
静态不可判：需要受控实验（外部改写 domain 文件后，本进程下一个 wave 是否覆写、是否出现两个相同 revision 的不同内容——对应 §8 不变量 9）。

### E. startup seed 与 cursor backlog

**E11 · 启动播种存在且语义正确（§5.4/§5.5 resume）—【等价实现】**
启动对 `ctx.sessions.list()` + 开域期间创建者逐个建 runtime 并播种 lifecycle 匹配的 stable（`T basic/service.ts:143-145`、`:187-196`、`:387-397`）；播种用 `runtime.stable === undefined` 守卫 ⇒ 恰好通知一次；不调模型、不重折、不重放未完成更新（模块头 `:11-20`）。cursor 从 `sourceCursor` 续接、只折 `seq > cursor`（`T basic/batch.ts:97-99`）。
Resume（同 id、同 `createdAt`+`cwd`）继续 stable，identity 不匹配视为新生命周期且**拒绝覆写**旧记录（`:455-465`、`:526-533`）——与 §5.5 Resume 条一致。

**E12 · `startupBacklogUpdate` 缺失：重启后积压不会自行成批（违反 §5.2 触发条、§8 不变量 11）—【确认差异】**
worker 构造时只把 `pendingEligible` 初值算出来（`T basic/worker.ts:103-108`），而 `maybeSchedule()` 的**唯一调用点**是 `session/event` 观察者（`T basic/service.ts:409-425`）；启动路径（`runtimeFor` / `installLifecycle`）没有任何一次调度尝试。
⇒ resume 后若 cursor 之上已积累 ≥ `minEvents` 的 eligible 事件且此后没有新的 eligible 事件到来，尾部**长期不折叠**，模型持续读到陈旧快照。理想 §5.2 要求"startup/resume：若 stable cursor 后存在 eligible backlog，主动 schedule 一次"；配置基线 §7 的 `startupBacklogUpdate` 在当前 schema 中不存在（`T basic/config.ts:17-29` 仅 11 键）。`16:77`、`:157` 已把同一事实列为待深挖，本轮在源码层闭环为【确认差异】。

### F. 多实例与单写模式

**F13 · 无租约/实例 id/fail-closed 协商（违反 §3.11 第 3 条）—【确认差异】**
插件全仓无锁获取尝试、无实例 id、无文件身份比对、无冲突检测（`16:88`、`:147-148`；本轮复核 `S` 内 `flock|lockfile|lease|instanceId` 零命中）。DSH 侧同样没有跨进程原语（`07:103`、`:167`）。域名是常量（`T basic/domain.ts:38`），进程内 `already-open` 只挡同进程第二次 open（`07:36`、`:182`）。
⇒ 第二实例既不 fail closed，也不报告；冲突只表现为"记录消失或被旧版覆盖"。这是 §3.11 第 3 条"必须 fail closed"的直接违反。

**F14 · 未启用 `storage-sqlite`（§5.4 "首选记录级 SQLite domain"）—【确认差异】+【构建产物差异】**
插件不写 `routes`、不引用 sqlite（本轮 `sqlite` 在 `src/**` 零命中；装配层 base 只挂 `storage-json`，`07:143`）。理想 §5.4 的首选后端因此完全未落地，且**不能被插件单方面落地**（需装配层 `routes` 或 `backend` 覆盖 + 手工迁移，`07:143`、`:192`）。
【构建产物差异】：`lib/tool-groups-*.js` 与安装副本的构建差异（`01:315-325`）意味着"当前工作区源码的存储路径"与"宿主实际装配字节"不是同一份；判读本主题结论时必须区分。另注：SQLite 后端的能力上限本身也有限——忙锁**立即失败**、无重试、无跨进程可见性（`07:108`、`:174`、`:185`），因此即便切到 sqlite，理想 §5.4 要求的 busy 有界退避与重新读取仍需**插件侧自行实现**。

### G. 写入持久性与介质身份

**G15 · 原子写不含 Windows write-through（§5.4 耐久性前提在 Windows 上不成立）—【确认差异】**
DSH `writeAtomic` 在 Windows 上跳过目录 fsync，rename 不带 `MOVEFILE_WRITE_THROUGH`（`07:93`；`storage-json/README.md:143`）。stable 与 audit 都是**权威数据**，而 session-log 侧反而有更严格的 write-through publish（`07:93` 对比段）。⇒ 掉电场景下目录项持久性无保证。另附【推导】：`publish()` 的 catch 覆盖 rename 之后的 `fsyncDirectory`，失败时内存回滚而介质已更新（`07:96`），该窗口会与"指针来自内存"叠加（见 D10）。

**G16 · domain 名/版本不可配置 ⇒ 无法按部署分片或冷热分离（§3.11 支持级别前提）—【确认差异】**
`name + version: 1` 是模块常量（`T basic/domain.ts:37-45`、`C tool-group-domain.ts:27-34`），路由只能用 `routes` 覆盖 backend，不能按 profile/workspace 分片（`07:132-134`）。理想 §3.11 的"单实例模式 vs 受支持的多实例模式"若要并存（例如 JSON 仅开发、SQLite 生产），先决条件是**同域可路由到不同后端**——这一条插件侧已具备（`routes` 是装配层属性），但**同域不同物理身份**无法表达。此处列为需基础设施决策的缺口，不是插件内的可修项。

### H. 工具 provenance 对 audit 的依赖

**H17 · 已提交 tool-summary 的 provenance 唯一来自 audit（违反 §6.1 / §8 不变量 5）—【确认差异】**
`buildSurfaceSourceIndex` 用 `toolSummaryReplacementSeqs` 判定 `tool-summary`；该集合来自 `servedReplacementSeqs(audit rows)`（`C source-index.ts:56-110`；`S compaction-basic.ts:725-734`）。Session replacement 事件**没有 producer 字段**，所以源码注释明确：缺少审计时第三方 replacement 必须保持 `unknown-replacement` 保护（`C source-index.ts:99-110`）。
⇒ §6.1 要求"replacement 的来源类型、source seqs、范围必须能从 Session 日志恢复"，当前**不满足**；§8 不变量 5"删除 audit 不改变 surface 类型判断"**不成立**：删除 audit 行会把已提交的 tool-summary 降级为 `unknown-replacement`，直接改变 `canCompactHistory` 的重入规则（`C source-index.ts:85-94`）与 §4.6 第 6 条的排除集合。

**H18 · 审计不可用时照常落 replacement（违反 §6.1 "不能只存在独立 storage audit"）—【确认差异】**
store 打开失败 → `toolGroupAuditStore = undefined` + 一条 warn（`S compaction-basic.ts:245-250`）。此后 `summarizeToolGroups` 在 `await this.toolGroupAuditStorePromise` 后直接 `return`（`:1091-1093`），但 pruner 与 history 路径不受影响：`sourceIndex` 退化为空集合（`:730-733`），`hasPendingToolIntermediateWork` 对 summarizer 位置返回 `'none'`（`:787`）。
⇒ 工具的**确定性裁剪**（把内容写入 Session log 的 `compaction/prune` + replacement）在 audit 完全不可用时仍会落地，其身份退化为 `tool-pruned`（由 shadow-price 前缀事件识别，`C source-index.ts:118-126`），属"弱身份"；而 semantic tool-summary 依赖 audit。理想方案要求这些 provenance 属于日志侧事实，audit 只作诊断（§6.2）。同一缺口使 §8 不变量 5 在"审计文件损坏/被覆盖"时失效。

**H19 · 审计失败路径的选择次序未定义（§3.7 / §6.2）—【需实验确认】+【参数差异】**
- 选择是**隐式**的：`successfulAuditFor` / `recoverableOpenAuditFor` 用 `Array.find` 取第一个匹配（`C tool-group-audit.ts:95-107`），依赖 `table.entries()` = Map 插入序 = JSON 文档键序（`16:48`）。记录**没有时间戳**（`C tool-group-audit.ts:17-33`），所以"第一条 open"是否总等于"最新 open"取决于整文件重写后键序是否严格保持。需一次构造同 fingerprint 多条 open 的实验（`16:172`）。
