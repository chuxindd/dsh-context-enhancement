## 2. E02 对原静态结论的修正

### 2.1 原判断中被反证的部分

此前把压力档概括为“whole-zone 一次语义压缩”，并进一步暗示其会常规跨过遗忘区边界。E02 使用真实 `planPressureSpan` 与 `compactIfNeeded` 的受控 fixture 后没有复现这一点：

- 88K 总量、缺口 8K 时，选中约 10K fixture token；
- 124K 总量、缺口 44K、遗忘区约 72K 时，选中约 46K fixture token；
- 多种 fixture 下跨度优先贴近 pressure deficit，未超过遗忘区。

因此“整区一次/必然跨区”不能再作为已发生的动态事实。静态审计应改写为：

```text
pressure path 在一次 invoke 中只提交一个 pressure span；
planPressureSpan 优先按 deficit + minimum span 选择第一个安全前缀；
没有 pressureExitRatio，也没有在同一次 invoke 内按退出线继续规划多个批次。
```

### 2.2 仍然成立的设计事实

E02 仍支持以下静态结论：

- 没有 `pressureExitRatio`；
- pressure invoke 提交一个 span 后返回；
- 普通 pressure 不使用 `maxPressureBatches` 进行循环；
- 实际释放目标是当前缺口，而不是固定的安全退出线；
- 是否形成“一个工具调用后再次压缩”仍需 E03 或真实轨迹确认。

### 2.3 E02 证据限制

- token 是 fixture price，不是 Provider token；
- fake LLM 只验证结构和体积，不验证摘要语义；
- fake measurement 不代表真实 system/tools/runtime context 包络；
- E02 只验证当前 pressure span 选择，不代表真实用户会话中的调用频率或净释放分布；
- “跨区代码路径存在”与“本 fixture 可达”必须分开记录。

## 3. E04/E05/E06 证据等级

### E04 Step 边界

这是有效的结构行为测试：真实 `Session` 与生产 planner 被调用，fixture 明确构造 user/message 不带 `turn/step`、同一步其他事件带字段。

但它证明的是：

```text
当前 payload 形状 + 当前 planner → 该切口被视为安全
```

它没有证明：

- DSH 真实事件流中该切口的比例；
- 真实 turn/step 结构是否总能由 fixture 还原；
- 用户问题与同一步回答是否实际被压缩到不同 replacement；
- 语义损失是否发生。

因此 E04 verdict 应是 `design-confirmed`，真实影响仍是 `inconclusive/需回放`。

### E05 Goal 大改

E05 的环境比纯函数测试更有价值：使用真实 Worker、filter、host、render 路径，但稳定存储与 LLM 是 fake。它可以确认当前实现的触发与合并行为：Goal 变化计一个 eligible 事件，不能单独绕过 `minEvents`，stable 没有 Host 权威 goalView，旧叙事可以继续被注入。

它不能证明：

- 真实 DSH goal 工具调用在所有入口都以相同事件顺序到达；
- 生产 storage 的重启和多实例行为；
- 真实模型会始终保留旧目标。

因此可标为 `design-confirmed + controlled-reproduced`，但不宣称 GUI 现象已复现。

### E06 TODO 清空

E06 是最确定的一项：生产 `filterEvent` 在空表上返回 null，worker 的 eligible watermark 不增加，已有 stable 不变。它证明的是当前设计行为，而不依赖真实模型。

需要注意：这只证明“插件侧不可观察清空”，不单独证明所有用户界面都会继续显示旧 TODO；后者还依赖 stable 已存在、注入路径和下一次请求。

## 4. Harness 设计评审

### 4.1 可接受部分

- harness 放在审计结果目录，没有改生产源码、现有 tests、package.json 或工作区 Vitest 配置；
- E02 使用生产 `planPressureSpan`、预算、replacement commit 关键路径；
- E05/E06 使用生产 Worker/filter/host/render 关键路径；
- E04 使用生产 Session 与 planner；
- 实验前后有 342 个文件 SHA-256 核对，`DRIFT=none`；
- 实验专用 Vitest config 没有污染工作区配置。

### 4.2 必须修正的部分

1. E02 spec 的注释和初始断言把“整区/跨区”写成预期，导致测试目标先于事实。以后必须把“待验证假设”和“判定规则”分开，允许反证。
2. E02 记录了选中跨度，但没有将完整结果账本统一写成每项 `result.json`；必须补齐落库后才能作为正式实验结果。
3. E04 只对 planner 的安全判定做 fixture 证明，不能把它命名成完整的用户问题复现；必须在 README 中明确 `design-confirmed` 与真实影响未证实的双层结论。
4. E05/E06 使用 fake worker environment，因此不能推出生产 storage/restart 结论；必须保留 fake 限制。
5. E01 依赖 audit store。不能继续使用“绕过构造函数后把 store 设为 undefined”的 fixture 来声称验证工具摘要；应使用临时 storage，或者明确只测裁剪分支并更改实验名称。
6. E03 必须记录每次维护的 before/after、选中 route tokens、摘要 output、净释放、headroom、两次维护之间的工具数量；不能只统计调用次数。
7. 实验目录的 `README.md` 和 `result.json` 尚未全部生成，当前 harness 文件不等于实验交付完成。
8. 任何运行输出中的“通过”只表示 fixture 断言通过，不表示理想方案通过，更不表示用户问题不存在。

## 5. 当前不应作出的结论

以下结论在本轮证据下不能直接作出：

- “压力档整区吞并已经复现”；E02 反证了这一表述。
- “压力释放问题已经解决”；E02 没有测真实净释放、退出水位或长期调用间隔。
- “Step 边界一定造成用户可见语义损失”；E04 只确认判定盲区可达。
- “Goal 更新一定没有保存”；E05 只确认不会走 urgent 通道，具体 stable 保存结果取决于后续事件和模型输出。
- “重启或双 DSH 的问题已经复现”；本轮未做生产 storage、多进程或真实 DSH 进程实验。
