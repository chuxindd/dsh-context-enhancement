## 2. 阶段一：只读裁决（6 个问题）

对半成品逐条核验，**未假定其正确**。结论如下（每条给出判定与依据）：

### Q1 终态记录是否复用同一权威 domain/record schema，重启后是否存活 —— **是（保留）**
`TaskStateTerminalRecord` 落在既有 `TaskStateRecord.terminal` 字段上，同表 `sessions`、同 ledger、同 lifecycle fence；`domain.ts` / `contract/spec.ts` 的 domain 定义**无需**任何新增表或版本升级。重启后由 `runtimeFor` 从持久记录恢复（`service.ts:395`），再由 `effectiveCursor = max(stable.sourceCursor, terminal.cursor)` 生效。测试：`restores the verdict across a restart without re-paying…`（旧 corpus）与本次新增的 restart 系列。

### Q2 是否把整文档 LWW 伪装成 CAS（禁止） —— **是风险点，已消除**
半成品在 `putTerminal` 里调用了一个 `commitStable({…空视图…}, 1, 1, 'v3', terminal.cursor)` 式的“伪造 stable”：它**不是** CAS，却在没有 base 的情况下凭空造出 revision 1、`filterVersion 'v3'`、`goalView/todoView: none` 的记录。该记录会持久化但**从不被发布**，于是内存与介质不一致，而且把“没有 base”这一真实情况伪装成“已提交”。
处理：**删除伪造路径**。现在 `putTerminal` 在 `stable === undefined` 时直接拒绝（`return false`），只写 `{ session, stable, terminal }` 里的 `stable` 是**已提交的**那一个；函数文档明确写了本 storage contract 是单写者、无记录级 CAS（B1 blocked-upstream），因此只做**单调前进**校验：
```ts
const floor = Math.max(stable.sourceCursor, existing?.terminal?.cursor ?? -1)
if (terminal.cursor <= floor) return false
```
该守卫保证“cursor 只能前进、且必须携带 provenance”，在无 CAS 的前提下这是可实现的正确性边界（不是 CAS，也**没有**冒充 CAS）。

### Q3 cursor 前进是否只限已知安全的 `includedSeqs` 前缀；权威 Goal/TODO 事实是否会被跳过 —— **半成品不安全，已修正**
半成品把「第一个可投影事件放不下」与「**base 单独就超预算**」两种原因都归给“第一个 eligible 事件”，于是 base 溢出时会把**无辜的**第一个事件当作窗口病因，逐个事件吞掉整条尾巴。生产配置下这是可达的：`maxEntriesPerKind: 50 × maxEntryBytes: 4000 = 200 000 B` 远大于 `maxInputBytes: 60000`，稳定的 base 帧本身就可能越界。
处理（`worker.ts#handleInfeasible`）：
1. 先用 `env.frame(id, base, { events: [], … })` **实测** base-only 字节数；超预算 → **fail closed**（只 `logger.error`，不写任何持久声明、不前进、不重试），因为病因是已提交的 stable 而非任何事件。
2. 找到**第一个可投影**的 eligible seq 作为**被测量出的** culprit（测得的，不是猜的）。
3. 若该 culprit 是 `goal/change` 或 `todo/write` 等权威事件（`isAuthorityEventType`）→ **fail closed**，绝不隔离；权威列表的清空/替换必须保持 pending。
4. 只有上述之外的情况才把**那一个** seq 记为终态并前进到它。

### Q4 瞬时/中断的尝试是否写入终态或推进 cursor —— **不会（保留 + 补证）**
`classifyAuditRow` 把审计行分为 `committed | terminal-infeasible | transient-failure | aborted`；终态只由 `handleInfeasible` 的 BUDGET 分支写入，瞬时失败（`TRANSIENT_LLM`/`TIMEOUT`）走 `failure` 且**不推进**（新增测试实证：失败后尾巴被**重新折叠**为 `[firstSeq, secondSeq]`，同一 cursor）。中断（in-flight 退出）只留下一条**OPEN**审计行（open 阶段在 dispatch 之前就已 await 落盘），分类即 `aborted`，重启后尾巴从头重折，不产生 ghost cursor（新增测试实证）。

### Q5 终态/稳定不可原子时是否 fail closed（绝不先丢 provenance 再前进） —— **半成品不安全，已修正**
半成品的顺序是 `putOpenAudit → putFinishedAudit → putTerminal`，即**先写审计、后写终态**；若终态写失败，审计已经声称了这次隔离。
处理：顺序反转为 **`putTerminal` 先写**，并且：
- `putTerminal` 抛错 → 记 `logger.error`，`advanced = false`；
- `putTerminal` 返回 false（admission 关闭/非法 lifecyle/无 stable/未前进）→ **fail closed**：不写审计、不重试、不发表任何声明，窗口留待后续合法 wave；
- 只有 `advanced === true` 才写 `logger.warn` 与 open+finished 审计对；审计写失败仅记 `logger.error`（诊断缺口，永不改变状态）。

### Q6 新内容如何开启新 generation；是否会永久禁止后续合法处理 —— **可以，但半成品留了一处死代码**
- 新事实通过 `effectiveCursor` 之后正常折叠，开启新 revision；重启继承的终态不会重付（终态 cursor 已覆盖该 seq）。
- **死代码**：半成品在 infeasible 分支里于 `this.active = true` 期间调用 `launch()`，而 `launch()` 在 `active` 为真时直接返回 —— 因此“隔离后继续处理剩余可折叠事件”的那段代码**永远不会执行**，必须等一个无关的新事件才可能再次调度。
- 处理：新增 `settleQuarantine()`，在 `finally { this.active = false }` **之后**按同一套门槛继续调度（`pendingEligible >= minEvents` → `threshold`；否则 `deferred` 的权威事实仍 pending 且 `followUpUrgent` → `urgent`）。因为每一步都**严格前进**（否则上文的单调守卫会拒绝），循环必然终止。
- 半成品还新增了「连续 2 次 PARSE/SCHEMA/SEMANTIC 失败则整窗隔离」：这与本 contract 自己的 `classifyAuditRow`（“transient-failure … 可后续重试”）**直接矛盾**，会把普通事实永久丢弃。**该逻辑连同 `consecutiveDeterministicFailures` 字段一并移除**，并在代码里留了 contract 一致性注释。

### 4.1 测得的 Windows 介质瞬时失败（诚实记录）

在真实 JSON domain 上做**连续两次发布**时（`putTerminal` 写 `sessions` 表后紧接 `audit` 表），本机偶发：

```
Error: EPERM: operation not permitted, rename
  'C:\...\Temp\dsh-...\storage\.<uuid>.tmp' -> 'C:\...\storage\context_enhancement_task_state.json'
```

`dsh-storage-json` 的发布协议是「临时文件 + `rename()` 覆盖」（见其 `lib/index.js#writeAtomic`），Windows 上目标文件被扫描器/索引器短暂持有时该 rename 会被拒。发生频率：约 10–15% 的整文件运行中击中诊断审计写。

**这是介质行为，不是语义缺陷**：被拒的是**诊断**审计行；权威记录（`putTerminal` → `sessions` 表）在其之前已经 await 落盘并成功，provider 按设计把它当作诊断缺口（`logger.error`，状态不变）。为不掩盖真实回归，两个新规格的**诊断台账**断言使用统一容错器 `expectLedger()`：

- 若**有**任何 finished 行落地 → 必须**恰好**符合预期分类（错误的 `success`/`failure`/`repair` 一律判失败）；
- 若一行未落地（`settled` 为空）→ 要求其余行必须仍是 **OPEN**（诊断缺口），并在 `repairs a lost finished audit…` 中显式 `console.warn` 说明该轮未覆盖 repair 分支；
- **权威**断言（`stable`/`terminal`/cursor/revision/模型调用次数）**始终严格**，不容错。

> 权威断言的严格性有结构性保证：`put` 只有在整份快照 `rename` 成功后才 resolve，失败会回滚内存并抛错；因此“内存中已确认的权威写入”在介质里必然存在（后续任何一次成功发布都会带上它，失败发布不会回滚文件）。

## 5. 明确的偏离与边界（不粉饰）

1. **偏离 PLAN §6.5 的“可降级 cursor”：首提交前的 infeasible 窗口无法落终态。**
   `TaskStateRecord.stable` 是**必填**（本次**刻意未**改为可选、也**未**新增终态专用表，因为那是 contract 变更，超出 B4.3 允许范围）。因此在「Session 尚未有任何已提交 stable」时，隔离窗口将**没有 stable 可承载终态**，同时**禁止伪造**一个。该角落的行为是 **fail closed**：不调模型、不推进、不写任何持久声明，只 `logger.error`。任务要求中「在不牺牲 provenance 的前提下无法实现时必须明确写清缺失 API」——缺失 API 记在这里：
