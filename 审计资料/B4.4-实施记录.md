## 0. 预审（先证能力，再写代码）

任务要求在动工前先确认两件事。结论如下，两项都是**实测**（读 `node_modules` 与真实探针），不是推断。

### 0.1 `StorageDomain` 是否支持新表 / 新 domain —— **支持**

`@deepseek-ai/dsh-storage-domain` 的 `defineDomain({ name, version, tables })` 接受任意表名与任意 stamp；JSON 后端（`@deepseek-ai/dsh-storage-json`）**由 domain name 直接推导文件名** `<name>.json`，并把 `{ unit: { name, version } }` 写进文档头。因此：

- 换 name = 换文件 = 旧文档**根本不会被打开**（这是本方案 clean-break 的杠杆）；
- 换 version = 同一 name 下的版本戳不匹配 → `parse()` 抛 `StorageError/version-mismatch`；当 domain 未声明 `invalidRecords` 时，**整次 open 被拒**（fail closed，不会跳过坏记录继续跑）。

### 0.2 一次 domain put 能否原子更新多张表 —— **不能（这是本方案的核心约束）**

实测调用链：`KvTable.put` → `unit.putRecord` → `dsh-storage-json#writeAtomic`（**临时文件 + fsync + `rename()`**）。在 `single` 布局下，**每一次表 put 都重发整份文档**。domain 层只在**单 domain 一条串行链**上排队，**不存在跨表事务**。

> 因此本 storage 契约里**唯一**的原子边界是 **「一张表里的一条记录」**。

这条约束直接决定了记录形状：**身份 + stable + 终态 + cursor 必须落在同一条 `sessions` 记录里**（见 §2.2）。诊断审计（`audit` 表）**永远是第二次 put**，因此**从不声称**跨表原子性 —— 丢一条审计行只是诊断缺口，绝不改变权威状态。

**能力已证明，未触发「必须停下写 blocker」的条件。**

## 2. 设计（每条要求 → 实现）

### 2.1 Clean break：新 domain 身份 + 新 schema

`basic/domain.ts`：

```ts
export const taskStateDomainSpec = defineDomain({
  name: 'context_enhancement_task_state_v2',
  version: 2,
  tables: { sessions, audit },
})
export const TASK_STATE_LEGACY_DOMAIN_NAME = 'context_enhancement_task_state'  // 仅诊断/测试引用，永不 open
```

- **旧记录不读、不迁移、不重写**：旧文档 `…/context_enhancement_task_state.json` 与新 name 推导出的文件名不同，本构建**没有任何代码路径**会 open 它。
- **戳不匹配 fail closed**：`version: 2` 使同名的错戳文档（例如被人手工改成 `version: 1`）在 `parse()` 阶段抛 `StorageError/version-mismatch`，整次 open 被拒，**不会**跳过坏记录继续。
- 该行为有实测测试：`never reads or rewrites the retired v1 document and fails closed on a mismatched stamp`。

### 2.2 无 stable 也能落终态，且**绝不伪造** stable

`contract/types.ts`：`TaskStateRecord = { session, stable?, terminal? }` —— `stable` 改为**可选**。

`service.ts#putStable` / `#putTerminal`：

- `putTerminal` **不再要求** 已提交 stable；记录写成 `{ session, terminal }`（无 `stable` 键），**不发明** revision/filterVersion/digest。
- 首提交前的窗口因此可以持久化终态；`effectiveCursor = max(stable?.sourceCursor ?? -1, terminal?.cursor ?? -1)`。
- `reconcileRepair` 对**无 stable** 的记录**提前返回**：不会伪造 repair 凭证去「修补」一个不存在的 revision。
- 终态在后续提交里**原样携带**（`putStable` 把 `existing?.terminal ?? runtime?.terminal` 写回同一条记录），因此一次提交既不会复活已隔离窗口，也不会丢掉块的类型化理由。

### 2.3 三种不可行病因，互不混淆（worker 实测，不猜）

`worker.ts#handleInfeasible` 现在按**实测量**分三支，**全部**落 typed 终态：

| 分支 | 触发条件（实测） | 终态 kind | cursor | blockSeq |
| --- | --- | --- | --- | --- |
| 1 | `frame(base, 空 events)` 字节数 > `maxInputBytes` | `blockBaseOverBudget` | **不动** | 无 |
| 2 | 第一个可投影事件是 `goal/change` / `todo/write` 等权威事实 | `blockAuthorityFact` | **不动** | 该权威 seq + type |
| 3 | 其他（普通事实单独放不下） | `quarantined` | 前进到**那一个**被测出的 culprit | — |

- 分支 1/2 的 cursor **严格等于** 当前 floor（`putTerminal` 强制 `cursor === floor`），因此块**永不**推进任何东西；被挡住的权威 seq **仍然 eligible、仍然 pending**，下一波（或下一个 generation）还能折。
- 分支 3 的 cursor **严格大于** floor（`putTerminal` 强制 `cursor > floor`），只跳**一个**被测出的 seq。
- 三支的 `reason` 都写明是**哪种**病因（base 字节数、权威 seq+type、或 culprit seq）。

### 2.4 Generation：块是「可重开」，不是「永久禁止」

```ts
generation = { baseSourceCursor, baseFilterVersion, baseDigest, maxInputBytes }
```

`sameTerminalGeneration` / `activeTerminalBlock`（`contract/spec.ts`，**纯函数**，service 与 worker 共享同一谓词）决定一个块是否仍然生效。块只在下列任一变化时**重开**：

- base 的内容/身份变了（revision → digest、sourceCursor 变）——普通提交、手动 `editStable`、恢复出的新 base；
- `filterVersion` 变（未来 filter 升级）；
- `maxInputBytes` 变（配置/预算）。

**其它一切都不重开**：时间流逝、重启、重放、同样的重放波次都不会。`putTerminal` 对**同一 generation + 同一 kind + 同一 blockSeq** 的重复块直接拒绝（`return false`），避免介质churn与重复记账。

### 2.5 启动不重付

`worker.ts`：构造期读一次 `env.activeBlock()`，**每一次 `launch()` 都重读**；块生效时直接 `recomputeEligible(); return` —— **不折窗、不调模型、不写任何东西**。

`service.ts`：新增 `currentGeneration(session)`、`refreshTerminalBlock(runtime, session?)`、`activeTerminalBlock(id, expectedSession?)`。刷新点是**发布已提交指针的那个唯一位置**（`publishCommitted`）以及记录落盘处（`putStable`）—— 因此**手动替换**（`editStable` 走 `publishCommitted`）与普通提交**同样**会重开一个块。这一条是本次实现过程中**实测发现**的缺陷：初版只在 `putStable` 里刷新，而 `editStable` 是「先 put 后 publish」，于是 `currentGeneration` 读到旧指针、块不解除。已修正并留下注释。

### 2.6 普通 culprit 仍然只隔离一个安全前缀 seq，provenance 同一次 put

`quarantined` 记录 `{ kind, requestId, generation, cursor, includedSeqs, code, reason, trigger?, time }`：cursor = culprit，“跳过”的正是**从 floor 到 culprit 之间投影为空**的那些 seq（安全前缀），不是整条尾巴。

### 2.7 写序：权威先行，审计在后

`recordVerdict` 先 `putTerminal`（权威），只有它返回 `true` 才写 open+finished 审计对。`putTerminal` 抛错 → `logger.error`、`advanced = false`、**什么都不声称**；返回 `false`（admission 关闭 / 生命周期不符 / 未前进 / 非法块）→ **fail closed**，不写审计、不重试、不声明。审计写失败仅记 `logger.error`（诊断缺口，永不改变状态）。

### 2.8 服务定义扩展（诚实说明）

`contract/index.ts` 新增两个**非抽象**方法 `getTerminal()` 与 `getActiveTerminalBlock()`（默认返回 `undefined`），provider `override` 之。之所以非抽象：B4.1/B4.2 的语义要求「只提供 committed stable 的替代 provider 必须继续可编译」，抽象化会把它变成破坏性变更。这是**新增只读方法**，未改任何既有语义。

## 4. 明确的偏离与边界（不粉饰）

1. **这是 clean break，不是兼容迁移。** 新 domain name + version 2 意味着**旧 v1 文档里的历史 committed stable 与台账在本构建里不可见**；受影响的大量测试 fixture 一并改到 v2 文档名（§1.2）。这是任务明确要求的「clean break」，**用于换取** 「无 stable 的终态有独立持久载体」与「块可 generation 重开」两项能力；旧记录**未被读、未被迁移、未被重写**（测试实证）。本记录不把它说成兼容升级。
2. **单写者 / 无记录级 CAS 的边界原样保留。** `putTerminal` 是「单 JSON unit 上的读-改-写」，**没有** revision 前置条件、**没有**冲突信号。多实例共享同一 medium 时，后写者会**静默**覆盖先写者的已提交记录 —— 本次**不**解决 B1，**保留并使其可测**（`still shares one medium … with no CAS` 测试显式断言「A 的 stable 被抹掉、A 仍在用内存指针、全程无任何报错」）。B1 结论仍为 **`blocked-upstream`**；本记录**不**声称任何 CAS。
3. **`blockBaseOverBudget` 在窄预算下仍会停滞该会话。** 它保证的是「**不误判病因、不吞事件、不伪造前进**」以及「generation 一变就重开」，**不是**「自动恢复」。base 帧本身超过预算的配置下，该会话会停到「base 内容变 / filterVersion 变 / 预算变」为止 —— 这是有意的取舍：宁可停滞也不静默丢弃事件。
4. **审计台账仍是第二次 put。** §0.2 已证明不存在跨表事务，因此**永不**声称跨表原子性；一次审计写失败只产生诊断缺口（`logger.error`），权威状态不受影响。
5. **服务定义新增两个只读方法**（§2.8）。这是契约**扩展**，不是语义变更；非抽象化是为了不破坏「只提供 stable 的替代 provider」的向后兼容。
6. 本记录**只**裁决 B4.4。**没有**任何断言称 B4 整体完成。
