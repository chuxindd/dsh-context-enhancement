## 1. 问题（单点）

`runtimeFor` / domain open / record hydration 之后，**cursor 之上已存在 ≥ `minEvents` 的 eligible 积压，但没有新的 Session 事件到来**，于是 worker 永远不会调用 `maybeSchedule()`：`session/event` 观察者是启动期唯一的调度入口。结果是重启后服务陈旧 stable，直到下一次 eligible 事件才顺带折叠积压（E07 已量化：2 010 ms 内零请求、零新 audit 行）。

### 3.1 两个实现要点（避免误判为「过度改动」）

1. **`countedThrough` 边界是必需的，不是清理性重构**：同一个 Session 在被 resume 时会二次经过 observer seam，构造期已计入的快照事件会被再次 `observe()`。没有该边界时 `pendingEligible` 会翻倍（构造计 6 + 重放计 3 = 9），直接后果是 `minEvents = 4`、真实积压 3 时**误发** startup 波——违反不变量 5。边界取「快照中 eligible 类型的最大 seq」（无则为 `-1`；seq 从 0 起，`-1` 是唯一安全的空哨兵）。实测修复后 `pendingEligible = 3`（此前 6）。
2. **worker 构造顺序**：worker 的初始积压计数在构造期一次性完成，所以必须在存储 stable 恢复**之后**构造。原先「先构造 worker、后恢复 stable」会让计数在 cursor = -1 下进行（把已提交前缀也算成积压），同样误发 startup 波。现改为：注册占位 runtime → 恢复 stable 并发布 → 构造 worker → 需要时排审计修复。

## 8. 一句话交付结论

修复只做了一件事：**在 runtime 建立（create/resume/open/hydration）之后，用真实 filter 算一次 cursor 之上的可投影积压，若 ≥ `minEvents` 就在 microtask 上发起恰好一波 `startup` 波**；恢复出的基线仍然先可发布，同步栈上零模型/零存储工作，空积压/低于阈值/domain 打开失败/lifecycle 不匹配都不发波，且不再依赖「追加事件来唤醒」。E07 同 fixture 对照从 `reproduced` 变为 `fixed`。
