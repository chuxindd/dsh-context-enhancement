## 1. 接口核对（实施前，只读检查 DSH checkout）

### 1.1 当前 Stable 注入在哪里 append

**不在插件里 append。** 插件 `./task-state-prompt` 只做两件事：

- `ctx.systemPrompt.context({ name: 'task-state:snapshot', order: 125, text: '{{task_state_snapshot}}' })`（`src/task-state-prompt.ts:56-63`）；
- `ctx.systemPrompt.variable('task_state_snapshot', …)` 读取 `ctx.get('taskState')?.getStable(sessionId)` 并返回 `renderTaskStateSnapshot(stable, maxBytes)`（`src/task-state-prompt.ts:64-72`）。

真正的 append 由 **DSH `@deepseek-ai/dsh-agent-loop`** 完成：

| 位置（DSH checkout `a66e4702`） | 行为 |
| --- | --- |
| `packages/core/agent-loop/src/agent.ts:239-249` | `systemPrompt.assemble()` → `renderContextSections(assembly)` → `RuntimeContextProjection.project(joinContextSections(sections), sections)`，只有**文本与 retained 不同**时才产生一条未提交的 `UserMessage` |
| `packages/core/agent-loop/src/agent.ts:288-293` | `step/start` 之后，对 `decision.messages` 逐条 `session.append('user/message', message, { surfaceOp: 'append' })` ← **唯一的 append 点** |
| `packages/core/agent-loop/src/agent.ts:355` | `this.session.deriveMessages()` 由 surface fold 得到模型请求消息；append 之后没有任何 await 前的插件钩子 |
| `packages/core/agent-loop/src/runtime-context.ts:25-76` | `RuntimeContextProjection`：`retained.text === snapshot` 时 `project()` 返回 `undefined`（去重），否则返回新消息 |

结论：插件**没有**任何合法位置可以把「DSH 自己 append 的那条 runtime-context 节点」改成 replacement：append 发生在 `turn()` 里、请求派生（`deriveMessages()`）紧随其后（同一同步栈），中间没有 waterfall/observer 可插。

### 1.2 runtime context 是不是 Session 事件 / Surface 节点

是。它是 `user/message` Session 事件，data 是 `UserMessage`，`source = { kind: 'plugin', plugin: '@deepseek-ai/dsh-system-prompt', form: 'snapshot', sections: [...] }`（`runtime-context.ts:68-74`），并带 `surfaceOp` 进入有序 surface。

- surface 是 append-only log 之上的有序视图：`packages/core/session/src/surface.ts`（`isSurfaceEligibleType` / `isSurfaceEvent` / `isAppendSurfaceEvent` / `isReplacementSurfaceEvent` / `applySurfacePlan`，476 行）；
- 只有 `user/message`、`assistant/message`、`tool/result` 可以带 `surfaceOp` / `sourceEventSeqs`（`packages/core/session/src/types.ts:373-419`）；
- 模型可见历史 = 对 surface 做 `deriveEventMessage` fold（`surface.ts:90+`），被 replacement 遮蔽的节点不再进入任何后续请求。

### 1.3 如何合法 replace

公开且被文档化的路径（`SurfaceOp` 注释原文：「Used by compaction; **any surface-replacing producer may use it**」`types.ts:395-404`）：

```ts
session.append('user/message', message, {
  surfaceOp: { op: 'replace', start: Seq, end: Seq },
  sourceEventSeqs: [Seq],
})
```

- `start`/`end` 必须都是**当前 surface 上存在的节点**；`start === end` 表示替换单个节点；`applySurfacePlan` 原地 splice，`surface.replaceGeneration += 1`；
- 生产参考实现：`packages/compaction/compaction-tool-result-pruner/src/index.ts:162-173`（真实的 surface-replacing producer，先 append 影子价格事件再 append 替换节点）。

### 1.4 sourceEventSeqs 要求

- replacement 节点：`sourceEventSeqs` 必须**非空**、**无重复**、只引用**严格更早**（`< 自身 seq`）的合法 seq，并且必须**包含每一个被遮蔽的 surface 节点**（`types.ts:395-404`、`SurfaceIntent` `types.ts:406-419`）；
- `append` 节点：`sourceEventSeqs` 可省略（省略即不声明来源）；若给出则必须非空；
- 空数组只有 `assistant/message`（已知空流）允许；非 surface 类型禁止携带该字段；
- 校验失败在 `session.append()` 同步抛出（日志不变，append 是原子的）。

### 1.5 session/event observer 重入限制

`Session.append()`（`packages/core/session/src/index.ts:668-719`）在发布期间置 `entry.appending = true`，观察者回调同步执行；**在发布栈内再次 append 会抛 `session append cannot reenter while another append is being published`**。因此：

- 不能在 `ctx.on('session/event', …)` 里 append replacement 来做「同栈内折叠」；
- 也不能靠「先 shadow DSH 节点、下一步再补」：`RuntimeContextProjection` 观察到自己的节点被 replacement 遮蔽时把 `retained` 置 `null`，而 DSH 的既定行为是**下一步无条件重新 append**（`packages/core/agent-loop/tests/loop.spec.ts:444-477`「re-emits unchanged runtime context when a surface replacement removed the retained snapshot」）。shadow DSH 节点不会收敛，反而每步新增一条。

### 1.6 resume / fork 的 lifecycle 身份

- **resume**：同 `SessionId` 的新 `Session` 对象（日志从持久化恢复）。lifecycle 身份由 `Session.header.createdAt` / `cwd` 表达，provider 用它做 fence（`src/internal/task-state/basic/service.ts:571-582` `recordFor`）；provider 侧 runtime 表按 `session.id` 索引并用 `runtime.session !== session` / `this.ctx.sessions.get(id) !== session` 做对象级校验（`service.ts:503-568`）。
- **fork**：`ctx.sessions.fork(source, boundary, childSessionId)`（`packages/core/session` SessionStore，`index.d.ts:420-434`）创建**另一个** Session 对象，继承源日志前缀（`inheritedEventCount` / `isOwnSeq`，`index.ts:611-626`）。子 Session 的 surface 里**包含**继承来的节点，但内存态绝不能跨对象复用。

### 1.7 核对结论（决定实现路线）

1. DSH 公开 API **无法**让 runtime-context 槽位变成 replacement（§1.1/§1.5），也**不允许**在 observer 内合法 append；因此**不能**继续用 `ctx.systemPrompt` 动态 context 作为 Stable 的模型可见投递通道，否则每个 revision 必然新增一条可见 snapshot（= E08）。
2. 合法且被文档化的 replacement 通道只有 `session.append(..., { surfaceOp: { op: 'replace', … } })`，**无需修改 DSH 本体**。→ 本批不触发 `B5.1-blocked.md`。
3. 因此 B5.1 把模型可见投递改为**插件自有的固定槽位**：槽位节点由插件在 `agent/pre-step`（`agent.ts:234-252` 的 step 边界，append 发布栈之外）创建 / replacement 维护；`task-state:snapshot` runtime-context 贡献仍然注册（模板与变量名保留），但其值恒为空串 —— 任何非空值都会重新进入 DSH 的 append-only projection（E08）。

## 2. 设计（目标不变量 → 实现）

| 目标不变量 | 实现 |
| --- | --- |
| 每个 live Session lifecycle 最多一个模型可见 Stable slot | 插件按 `session.id` 维护内存记录（对象 + `createdAt` 双重 fence），每一步在 **`agent/pre-step`** 解析「本 Session 自己 surface 上可见的 slot 节点」：0 个→创建/重建，1 个→（revision 变化时）replace，>1 个且连续→一次 range replacement 折叠 |
| 首次创建 slot，后续 revision 必须 replace | 首次 `surfaceOp: 'append'`；后续 `surfaceOp: { op: 'replace', start: slot, end: slot }` + `sourceEventSeqs: [slot]` |
| replacement 元数据 | `source.kind = 'task-state-slot'`，携带 `slotId`、`sessionId`、`lifecycleCreatedAt`、`generation`、`revision`、`previousRevision`、`previousGeneration`、`digest`、`sourceCursor`、`coveredSeqs`（= 被遮蔽 surface 区间）；`sourceEventSeqs` 为事件字段本身 |
| generation 单调 | generation = 1 + 本 Session **整条日志**内所有 slot 节点的最大 generation，并且 ≥ 记录 generation + 1；resume/fork 后继续单调 |
| 失败 / 槽位缺失 / 被其他 surface 操作移除 | replace 抛错 → 局部捕获、计数、**不 append**（surface 不变，模型继续看旧槽位，fail closed）；槽位消失 → 安全重建（append 新节点，generation 继续单调）；出现多个可见 slot 且**连续** → 一次 range replacement 折叠为 1；不连续（中间夹着非 slot 节点，range replacement 会误伤真实内容）→ fail closed，不新增 |

### 4.2 关键实现决策（以及为什么）

1. **投递通道换成插件自有槽位**：DSH 只会 append 自己的 runtime-context 节点（§1.1），遮蔽它还会让 DSH 每步重新 append（§1.5）——所以 `task-state:snapshot` 的**变量值恒为空串**。渲染器与预算语义不变，渲染结果改由插件写进自己的 `user/message` 槽位节点（`source.kind='task-state-slot'`）。
2. **维护点在 `agent/pre-step`**：这是唯一「append 发布栈之外、`step/start` 之前、请求派生之前」的合法边界。`kind === 'reject'` 与 `signal.aborted` 不注入（不产生请求）；`kind === 'enter'` 即使 `messages` 为空也**照常**维护（`enter` 本身就意味着一次模型调用，`deriveMessages()` 会带上 runtime-context 占位）。
3. **槽位身份只依赖日志**：`slotId` 是常量通道标识，`generation` = 本 Session **整条日志**内最大 generation + 1，因此 HMR 重挂、进程重启、resume、fork 之后都不会回退，也不需要迁移任何旧数据（PLAN §11 clean break）。内存表只做「同一 lifecycle 内避免重复读渲染」的短路径，键为 `session.id`，并用「Session 对象同一 + `header.createdAt` 同一」双重 fence。
4. **fail closed 优先于可见性**：replace 抛错 → 计数 + **不 append**（surface 保持原样，模型继续看上一 revision，下一步重试）；可见 slot >1 且**不连续** → 计数 + 不 append（range replacement 会误伤真实内容）；`getStable` 返回 undefined（lifecycle 不匹配）→ 什么都不做。
5. **诊断读取用 `ctx.root` 作为键**：`ctx.plugin()` 给插件的是子 context，宿主/测试拿到的是根 context，故注册表按 `ctx.root` 分桶、每个 mount 一个独立 `Map`（dispose 只清自己那一份）。

### 4.4 行为变化（显式登记）

1. **assembly 不再携带 stable**：`renderContextSnapshot(assemble())` 现在恒为 `''`（`task-state:snapshot` 条目仍注册、模板仍是 `{{task_state_snapshot}}`、变量仍存在但值为空串）。旧用例「renders the stable for the session…」「bounds the rendered variable value…」「reads only the task-state pointer during assembly — one synchronous getStable call」因此**必须**改写：
   - 渲染文本与字面 `{{…}}` 保留、字节预算 → 改为直接断言 `renderTaskStateSnapshot()`（同一生产渲染器，语义不变）；
   - 「assembly 每次同步读一次 `getStable`」→ 改为「assembly **零次**读取」（指针读取移到 step 边界，即槽位维护点）。这是 B4「assembly 不碰存储」的加强版，不是回退。
2. **注入位置提前到 step 边界**：槽位节点在 `agent/pre-step` 内 append，因此它排在 `step/start` 与该 step 的 claimed 消息**之前**，并在后续 replacement 中保持原有 surface 位置。非 turn 期写入插件来源的 `user/message` 合法（`session/invariant.ts` 对 `user/message` 无 turn 约束），且该来源不会被任务状态折叠吸收（`filter.ts` 的 `directHumanKind` 只认 `kind:'user'|'goal'`，故不产生自反馈）。
3. **旧的（升级前）会话**：其 runtime-context snapshot 节点是 DSH 自己的节点，本批不做遮蔽（遮蔽会让 DSH 每步重新 append）。因为变量恒为空串，DSH 在「曾有 retained 快照」的会话上会追加**一次** `CLEARED` 标记（`runtime-context.ts:13/66`），此后不再新增；新会话则一次也不会出现。属于 clean break 下的预期表现，已登记。
4. **文档漂移（未改，属允许清单之外）**：`presets/contextual/agent.cordis.yml` 里关于 `task-state:snapshot` 会渲染 stable 的注释、以及 `CHANGELOG.md` 中同一描述的条目，现在只描述「注册保留、渲染为空」。这两处不在 PLAN §7 的文件清单内，故本批未改。

### 4.5 已知边界（未做，非缺陷）
