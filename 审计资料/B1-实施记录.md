## 1. DSH storage API 能力判定（源码证据）

对 DSH HEAD `a66e4702` 的只读检查。判定只依据源码/类型契约，不依据注释里的设计意图。

### 1.1 结论速览

| 能力 | 是否原生提供 | 证据 |
|---|---|---|
| 跨进程 CAS / `expectedRevision` / revision compare | **否** | `dsh-storage-domain` `put` 无任何前置条件；`dsh-storage-json` 与 `dsh-storage-sqlite` 写入均为无条件整条 upsert |
| refresh / reopen（已打开 domain 或 table 重新读取介质） | **否** | 域内存表只在 `open()` 的 `loadAll()` 时播种一次；`KvTable` 无 refresh/reload/reopen 成员；唯一"重新读取"手段是关闭并重新 `open` 整个 domain |
| single-writer / 单写者声明 | **否**（只有同进程守卫，不是跨进程保护） | `JsonStorageBackend.open` 的 "exactly one live handle" 是**单个 backend 实例**内的 `Map` 守卫；`DomainFacility` 的 `already-open` 是**单个 facility 实例**内的 `Set` 守卫。两者都不跨进程、不跨 registry 实例 |
| 冲突信号 / 结构化 conflict | **否** | 无冲突概念；`put` 只有 resolve/reject 两种结局，reject 只来自介质错误（`closed`/`malformed-medium`/`version-mismatch`） |
| fail-closed（版本/形状不符即拒绝） | **是** | `version-mismatch`、`invalid-record`、`malformed-medium` 三处硬失败，且插件已在 `service.ts` 的 open 失败分支把整个 provider 置为永久 disabled |

### 1.2 逐条源码证据

**（a）`KvTable` 没有 CAS，也没有新鲜度。**

`packages/storage/storage-domain/src/domain.ts`：

- `put(key, value)`：`await this.host.unit.putRecord(this.tableName, key, value)` → 无条件整条 upsert，无 `expectedRevision`、无 base 比较。
- `update(key, fn)`：注释明确"Atomic read-modify-write on the domain's write chain … so concurrent updates never interleave"。**这是单进程内的一条写链**，不跨进程；`fn` 看到的是内存当前值，而内存值只在 open 时从介质播种。
- `KvTableImpl` 的 `records` 是 `Map`，由构造参数注入（`DomainFacility.open` 里 `await unit.loadAll()` 的产物），此后**只有本次写入会更新它**，没有任何重新读取路径。
- `DomainFacility.open`（`storage-domain/src/index.ts`）里 `loadAll()` 是**唯一**一次介质读取；`Domain.close()` 之后名字才释放，因此"重新读取"= 关闭并重开 domain。

**（b）JSON 后端整文档写、无跨进程协调。**

`packages/storage/storage-json/src/single-unit.ts`：类注释自述 "The in-memory state is authoritative; every write primitive mutates it and republishes the whole file atomically. Writes are NOT queued here"。`openSingleUnit` 只在 open 时 `readFile` 一次。

`packages/storage/storage-json/src/atomic.ts`：发布协议为"同目录临时文件 → fsync → `rename()` 覆盖"。注释自述前提是 "a unit file has exactly one writer per process and last-write-wins is correct"——这正是 E10 证明在双写者下失效的前提。`writeAtomic` 里没有任何 `flock`/锁文件/独占句柄。

`packages/storage/storage-json/src/index.ts`：`open` 的并发守卫是实例字段 `open`/`opening` 两个 `Map`，并在源码注释里被明确称为 "Double-open is a caller bug, not a medium condition"——即它**不认为**介质层需要检测第二个写者。

`packages/storage/storage-json/README.md`：只把 `single` vs `per-record` vs SQLite 当作布局/性能选择。

**（c）SQLite 后端同样没有 CAS。**

`packages/storage/storage-sqlite/src/unit.ts`：`upsert` 语句是 `INSERT … ON CONFLICT(key) DO UPDATE SET value = excluded.value`——**无 `WHERE` 前置条件**，因此即使换用 SQLite 路由也得不到 CAS。同文件注释："Each primitive is a single statement, so atomicity comes from SQLite itself — no explicit transactions, and no write queue"。

**（d）DSH 自己把"跨进程 revision 模式"登记为未落地项。**

`packages/storage/storage-domain/README.md` Known Limitations：

> **Single-process change visibility** — `domain/changed` is an in-process event; a second host process or a reconnecting GUI observes no changes **until the cross-process revision pattern lands**（引用 `.agents/notes/proposed/architecture/2026-07-24-domain-kv-storage-and-workspace.md`）
> **No data migration** — a domain whose stored version differs from its spec rejects at open (`version-mismatch`)

即：跨进程 revision 模式是**上游 proposed**，当前 API 不存在。

**（e）插件装配边界上没有介质身份。**

插件拿到的是 `ctx.storageDomain`（`DomainFacility`）。`StorageJson` 的 `root` 是 `JsonStorageBackend` 的私有构造参数，没有 getter、没有暴露到 `Domain`/`KvTable`/`KvUnit` 的任何成员。因此插件**无法知道域文档在磁盘上的位置**，也就无法在插件侧放置一个位于同一介质、能被第二个写者观察到、且不依赖插件自身配置的"介质级"守卫。任何以插件新配置项给出的锁/守卫路径，在"两实例配置不同"时双方各自成功——**等于没有保护**，属于被 PLAN §3 明令禁止的伪装。

### 1.3 判定

- 跨进程 CAS、revision compare、refresh/reopen、single-writer/fail-closed 四类能力中，**只有 fail-closed 存在**（且以"拒绝打开"的形式存在）。
- 因此 PLAN §3 目标不变量中的"单写 JSON 模式必须显式 `singleWriterOnly`，第二写者不能静默运行"与"多实例提交必须带 expectedRevision，同 revision 只有一方成功"**在当前 API 下没有可实施的承载**。
- 插件侧唯一真实可用的跨进程原语是**文件系统**，而插件没有介质路径；用进程内 mutex、时间戳、或"读一次再写一次"（DSH 的读是内存权威，不是介质读）都不构成跨进程保护。按 PLAN §3 停止条件与用户指令，**不做这三类伪装**。

### 2.3 clean-break 处理

用户口径：不兼容旧版本插件数据。**本批没有引入任何新 schema/version，因此不需要 clean break 的落地动作**；但 clean break 所需的机制已由现有 API 提供并经上面 clean-break 1/2 用例实测确认：

- 旧 domain 文档被新 version 声明打开时 `version-mismatch` 硬拒绝（无需 `compatibleVersions`、无需 migration、不会被当成空 store）；
- 新 schema 缺字段/形状不符时 `invalid-record` 硬拒绝，且现有 `service.ts` 已把 open 失败变成 provider 级永久 disabled（不服务 stable、不装 observer/worker、不再二次打开、不调用模型修复）；

## 7. 上游接口缺口（建议提交 DSH 上游，本批不改 DSH）

要让 B1 可实施，至少需要下面任意一组能力（保持 DSH checkout 只读，本批只登记需求）：

1. **记录级 CAS**：`KvTable.put(key, value, { expectedRevision })` 或 `compareAndSwap`，不匹配时返回结构化 conflict（而不是普通成功）。最小可用形态是 `KvTable.updateIf(key, predicate, transform)` + 明确冲突错误码。
2. **介质新鲜度**：`Domain.refresh()` / `KvTable.reload(key)` / `KvUnit.loadAll()` 的再读入口，使已打开实例能在提交前重新读取可验证的介质 revision。
3. **单写者租约或等价 fail-closed 通道**：由 DSH 侧（而非消费插件）持有介质身份，例如 `StorageBackend.acquireWriter(unitName)` 返回租约句柄、失败即拒绝，且租约语义（阻塞/失败/超时接管）由上游定义。
4. **（可选，成本更低但不充分）**把权威表改成 `per-record` 布局：可消除 R-P0-1/R-P0-3 的"整文档覆盖抹掉其他 key"部分，但**不能**解决同 key 分叉（R-P0-2）与 stale view（R-P0-4），且需要配套的 domain version bump。本批不擅自实施，因为它会改变介质形状并由 A/B 实验之外的判据验收。

## 8. 下一步建议（供主代理决策，不在本批执行）

1. **推荐**：把 §7 的 1/2/3 作为 DSH 上游接口缺口提交，B1 保持 blocked；在缺口落地前，任何"多实例可用"的声明必须撤回。
2. 若产品接受"单写者"作为硬前提：需要一个位于**同一介质**、且第二个写者必然可见的守卫。这要求 DSH 暴露介质身份（§7.3），否则插件侧无解；不要在插件配置里放锁路径（配置不同的两实例会各自成功）。
3. 若接受"降低损失面但不宣称安全"：可评估 §7.4 的 `per-record` 迁移，但必须单独成批、单独验收，并明确它**不**满足 E10 的 C2/C4。
