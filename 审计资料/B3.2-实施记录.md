分类口径：

### 2.1 实现缺陷（3 项，改生产代码）

#### B-impl-1 — `no-progress` 在同一状态被记录两次

- 现象（基线实测）：同一 surface 状态下 `stops` 为 `['no-progress','no-progress']`。
- 根因：`no-progress` 分支在调用统一停点漏斗 `stopEnvelopeBudgetPass(...)` **之后**，又显式调用了一次 `logStop('no-progress')`，绕过了漏斗的去重记忆。
- 违反的不变量：单一停点漏斗（每个 (reason, pressure/surface) 状态只记一次）。
- 修法：删除 `no-progress` 分支里多余的那次 `logStop`；该分支现在只走漏斗（`src/compaction-basic.ts` 第 1037 行）。
- 证据：`tests/compaction-envelope-budget.spec.ts` 的 "terminates a repeated no-progress pass within one surface generation" 现在期望 `stops` 长度为 1。

#### B-impl-2 — 计划受阻时经两条路径重复上报

- 现象（基线实测）：`envelope-dominated` 与若干 `plan.reason` 在 `stops` 中出现两次。
- 根因：受阻处理分支先把 `plan.reason` / `activeVeto` 交给漏斗，随后又无条件 `logStop(reason)`。
- 违反的不变量：单一停点漏斗 + 每个状态只上报一次。
- 修法：统一受阻处理 —— 先算出 `const reason = activeVeto ?? plan.reason`，**只**经漏斗上报并 `finishLedger(reason, false)`，删除单独的 `logStop`（`src/compaction-basic.ts` 第 923 行是唯一入口）。
- 证据：`tests/compaction-envelope-budget.spec.ts` 的 "vetoes an envelope-dominated pass once per pressure/surface state"。

#### B-impl-3 — 一次"收窄后成功付费"的批，被当成 pass 的终止原因上报

- 现象（基线实测）：`budget.deferred` / `budget.withheld` 类原因出现在 `pass.stops` 中，而该 pass 实际上**成功压掉了一段 span** 并继续/结束于别的原因。
- 根因：`activeVeto` 一旦被设置就在循环末尾无条件作为 pass 停止原因上报，没有区分"这次收窄随后被付费"与"这次收窄真的把 pass 卡死"。
- 违反的不变量 4（同一 pass 的替换不得被折叠进后续批次）与"停止原因必须反映真正终止 pass 的原因"。
- 修法：`activeVeto` 在为后续 span 付费后**重置**；只有"受阻后再没有任何可付批次"时，该 veto 才作为终止原因经漏斗上报（`src/compaction-basic.ts` 第 923 / 935 / 948 / 972 / 995 行构成统一路径）。
- 证据：
  - `tests/compaction-envelope-budget.spec.ts` > "compacts the safe prefix before a reentry blocker instead of deadlocking"：宽 span 被 blocker 否决 → 收窄到 `0..4` 并**付费**，本次收窄**不**上报；随后批次计划起点落在 blocker 上、无任何可付前缀，此时才上报 `'reentry-deferred'` **一次**。
  - `tests/compaction-reentry-liveness.spec.ts` > "does not carry over actionable tool debt veto to a clean narrowed prefix"：收窄后的干净前缀被付费，终态为 `['tool-stage-deferred']`（恰好一次）。

### 2.2 旧契约断言更新（13 项）

共同根因：旧断言按 `thresholdTokens`（压力触发线 80）与 40 token 差额、或按"单批 = 一个固定下标"写死。冻结后的语义是：

- 计划目标改为**退出线** `exit = min(thresholdTokens, floor(W × pressureExitRatio))`，默认 70；
- `reclaimTokens = totalTokens - exit`，严格目标 `reclaim + minSpanTokens + 1`；
- 有界批次循环每批重新测量、重新计划，且 `minStartIndex` 跳过本轮自己产出的替换。

### 2.3 B13 的实测流程（因为它最容易讲错）

用与 spec 完全同构的临时探针（复用同一 fake `sourceIndex`、同一 `canCompactHistory`）打出中间量：

```
spec {"threshold":800,"exit":700}
step1 start {"nodes":30,"total":1040}
  PAID {"call":1,"s":0,"e":4,"spanTokens":100,"totalAfter":950,"nodesAfter":26}
  STOP-LOG reentry-deferred
step1 ledger {"beforeTokens":1040,"afterTokens":950,"batchesRun":1,
              "netReleaseTokens":90,"exitReached":false,
              "terminalReason":"reentry-deferred","stopReasons":["reentry-deferred"]}
batch2 state {"total":950,"nodes":26,
              "zones":{"forget":{"s":0,"e":12,"t":250},"tool":{"s":13,"e":15,"t":60},"recent":{"s":16,"e":25,"t":200}},
              "bcap":240,"minStartIndex":1,"reclaim":250}
batch2 plan (minStartIndex=1) {"kind":"selected","range":{"startIndex":1,"endIndex":12,"startSeq":6,"endSeq":17,"tokens":240}}
step2 result {"paid":[{"s":0,"e":4}],"stops":["reentry-deferred"],"total":950}
```

关键点：
1. 宽 span（`0..11`，240 token = Bcap 前缀）被 node 5 的永久未知替换否决 → 收窄到 `0..4` 并**付费**（100 token，落地 950）。付费使得该次收窄**不是**终止原因（B-impl-3）。
2. 第二批的计划 `startIndex` 由 `minStartIndex` 推进到替换之后（= blocker 自身的位置），因此候选序列集合为空 —— 这个 surface 状态**没有任何**可付前缀，宽的和 1 节点的都没有。此时 blocker 才成为真正的终止原因，且经漏斗**只上报一次**。
3. Step 2 的 surface 状态与 Step 1 结束时相同（950 token / 26 节点），去重记忆命中，所以 `stops` 不增长。这同时验证了"重入时不会伪造新 pass 停止"。
